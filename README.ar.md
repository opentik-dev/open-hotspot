# Open-HotSpot — التوثيق العربي

طبقة إدارة LuCI محلية لـ **openNDS** على OpenWrt. توفر إدارة الحسابات، ملفات
السرعة والحصة، القسائم، والأجهزة المرتبطة بالحساب، مع قاعدة SQLite محلية.

## الحالة الحالية

- الراوتر الاختباري: Linksys EA8300، إصدار OpenWrt 25.12.5.
- عنوان الإدارة يحدده إعداد LAN الحالي؛ استخدم متغير `TARGET_IP` في أوامر
  التشغيل، ولا تعتمد على عنوان ثابت.
- مصدر الإنترنت العلوي يمكن أن يكون Wi‑Fi أو Ethernet أو DHCP متغيرًا؛ ولا
  يدخل عنوانه في عقد FAS المحلي.
- آخر حزمة مرشحة: `luci-app-open-hotspot 1.2.0-r60`؛ وهي تتضمن عزل شبكة
  العملاء/إنترنت الأشياء واستعادة جاهزية openNDS، بينما r51 هي النسخة المثبتة
  السابقة على الراوتر.
- إعداد FAS المحلي محفوظ على المنفذ `2080` والمسار `/nds/fas.php`، لكن سجل
  كان الاختبار الأخير يثبت دخول openNDS في `exit_code=139`؛ عالجت r58 ذلك
  بإصلاح توافق init/procd المثبت على الراوتر، وأصبح `ndsctl` مستقرًا.
- `dnsmasq-full` مثبت مع دعم `nftset`، لكن ذلك أغلق فجوة الميزة فقط ولم يغلق
  عطل openNDS المستقل في الإقلاع/إعادة التحميل (`exit_code=139`).

الحزمة المختبرة موجودة في
[`dist/luci-app-open-hotspot-1.2.0-r60.apk`](dist/luci-app-open-hotspot-1.2.0-r60.apk)،
وتسجل بصمة SHA-256 بعد البناء في `dist/SHA256SUMS`.

يضيف r51 تشغيل setup الأساسي تلقائياً أثناء تثبيت/ترقية الحزمة، وفحص جاهزية
openNDS عند تشغيل خدمة Open-HotSpot إذا كان FAS المحلي
مفعلاً، فوق حماية r47 idempotent لسماح FAS وانتظار r45 لجاهزية openNDS ضمن نافذة
الإقلاع المرصودة واكتشاف واجهة LAN
من UCI، فوق قابلية التشغيل المباشر لفحص فصل الشبكات وحارس العنوان الديناميكي
لـ FAS ووظائف r39،
فيمنع تكرار العنوان المحلي وتساوي LAN مع البوابة الافتراضية وتداخل شبكة LAN/WAN.
ويضيف r52 خياراً في صفحة Setup لمنع أو السماح بوصول شبكة عميل مخصصة إلى منافذ
إدارة الراوتر 22/80/443 دون الاعتماد على عنوان IP، مع رفض تطبيقه على نفس جهاز
`br-lan` حتى لا ينقطع وصول الإدارة. تفاصيل WARP وشبكة IoT في
[`docs/router-access-and-iot.md`](docs/router-access-and-iot.md).
ويضيف r53 إزالة سباق إعادة التشغيل أثناء ترقية الحزمة وفحص الجاهزية الدوري
مع تنظيف socket المؤقت القديم عند الحاجة.
ويضيف r54 انتظار openNDS إذا كان في إقلاعه الطبيعي قبل محاولة إعادة تشغيله.
ويجعل r58 فشل حارس العزل يعود بخطأ قبل أي تعديل في firewall، ويعالج توافق
تشغيل openNDS مع procd على الراوتر المختبر.
وتتضمن وظائف r39 التجديد
الإداري للحصة وإعادة ربط MAC بشكل صريح ومدقق، إضافة إلى
ترقية مخطط قاعدة البيانات إلى v4، فوق وظائف r36 السابقة.
وقد ثُبّتت r58 فعلياً على الراوتر وتحققت migration وواجهات RPC وحارس منع
الإدارة المعزولة. أما اختبار البوابة الحي فما يزال متوقفاً بسبب عطل openNDS
المسجل في E-009.

سجل الحزم والإصدارات المحفوظة موجود في
[docs/release-history.md](docs/release-history.md).

يتحقق الإصدار r51 من حمولة FAS الموثقة التي تستخدم الحقل `hid`، ويقبل أيضاً
التسمية التوافقية `client_hid` التي ظهرت في بعض مسارات العميل captive portal.
أما الطلبات التي لا تحمل سياق FAS موثقاً فتبقى مرفوضة لأسباب أمنية.

## عقد عناوين بوابة الدخول

صفحة حالة عميل openNDS المدمجة متاحة على العنوان
`http://status.client`، ويعيد openNDS ربط هذا الاسم بعنوان بوابة الراوتر
الحالي وقت التشغيل. أما صفحة تسجيل الدخول العربية/الإنجليزية التي أُنشئت في
المشروع فتخدمها نقطة FAS المحلية `/nds/fas.php`، لكن يجب الوصول إليها عبر
تدفق بوابة openNDS حتى تصلها بيانات سياق FAS الموثقة.

لذلك فإن فتح `/nds/fas.php` مباشرةً، أو فتحه من فحص captive portal لا يرسل
حمولة FAS، يعرض عمداً صفحة الخطأ المنسقة «بيانات FAS الناقصة» ولا يقوم
بمصادقة العميل. استخدم زر **فتح بوابة الدخول** في الصفحة، أو افتح
`http://status.client` عبر HTTP العادي، ثم أرسل نموذج الدخول.

إعداد FAS المحلي لا يثبت `fasremoteip` ولا `fasremotefqdn`. لذلك تغيير الراوتر
العلوي أو عنوان WAN لا يتطلب تعديل FAS. يجب أن يتصل العميل بشبكة
Open-HotSpot المُدارة على `br-lan`؛ الاتصال بواي فاي الراوتر العلوي يتجاوز
openNDS.

الصورة التي تعرض بطاقة «بيانات FAS الناقصة» هي صفحة تشخيص آمنة ومغلقة
افتراضياً، وليست دليلاً على غياب صفحة FAS من حزمة APK. الصفحة غير المنسقة التي
ظهرت كانت صفحة openNDS أثناء حلقة إعادة التشغيل؛ بعد r51 تم التحقق من عمل CSS
والصورة وإعادة التوجيه إلى FAS. وما يزال اختبار العميل الفعلي المتبقي هو إتمام
التسلسل: البوابة → تسجيل FAS → ظهور العميل بحالة `Authenticated` في openNDS.

## التوزيع عبر GitHub

صفحة **Packages** تبقى فارغة بشكل صحيح؛ GitHub Packages لا يدعم صيغة APK
الخاصة بـ OpenWrt ضمن سجلاته المدعومة. الحزمة موجودة داخل المستودع، وأضفت
Workflow ينشرها تلقائياً كملف مرفق في **Releases** عند دفع وسم يبدأ بـ `v`.
راجع [صفحة الإصدارات](https://github.com/opentik-dev/open-hotspot/releases).

تم حفظ نسخة احتياطية قبل التغيير، كما تم أرشفة حالة التطبيق القديم. لم يُنفذ
مسح مصنع حرفي حتى تبقى استعادة الاتصال عبر LAN وSSH ممكنة.

## التثبيت

```sh
TARGET_IP=<current-management-ip>
tar -C dist -cf - luci-app-open-hotspot-1.2.0-r58.apk | \
  ssh root@"$TARGET_IP" 'tar -xf - -C /tmp'
ssh root@"$TARGET_IP" 'apk add --allow-untrusted /tmp/luci-app-open-hotspot-1.2.0-r58.apk'
```

بعدها افتح: **Services → Open-HotSpot → Setup**. أنشئ أولاً شبكة/SSID أو VLAN
مخصصة لأجهزة IoT، ثم أدخل اسمها في خيار **Managed client network** واختر منع أو
سماح وصول صفحة الراوتر، واضغط التطبيق. التفعيل المحلي الصريح:

```sh
ssh root@"$TARGET_IP" '/usr/lib/open-hotspot/activate-local-fas.sh enable'
```

للتراجع:

```sh
ssh root@"$TARGET_IP" '/usr/lib/open-hotspot/activate-local-fas.sh rollback'
```

## ما تبقى قبل التسليم

يلزم اختبار عميل Wi‑Fi/LAN منفصل يمر فعلياً بتسلسل captive portal → FAS →
BinAuth → جلسة openNDS، ثم اختبار الحصص وتعدد الأجهزة والقسائم. كما يجب تعيين
كلمة مرور root. تفاصيل الاختبارات ونسخ الاستعادة وSHA-256 موجودة في
[`specs/001-open-hotspot/quickstart.md`](specs/001-open-hotspot/quickstart.md).

للتجربة الحالية اتصل بشبكة الاختبار، ثم أعد فتح صفحة
الدخول إذا كانت مفتوحة قبل تثبيت r55، وسجّل بالحساب التجريبي الذي أُنشئ على
الراوتر. لا تُعدّ التجربة مكتملة حتى يظهر العميل `Authenticated` في
`ndsctl status`.

طريقة بناء SDK/feeds موثقة مع روابط OpenWrt الرسمية في النسخة الإنجليزية من
هذا الملف.
